# 从零理解 SentinelLab，再准备简历和答辩

## 先用一句话理解

这是一个给 AI 助手做“交付前考试”的平台。它让助手做客户规定的题，记录怎么做的、回答依据在哪，然后判断这个版本是否值得交给客户使用。

不必从 FastAPI、数据库和队列开始。先打开交付页面，想象你是一个客户：你有资料、有业务规则，需要一个助手帮你查资料和准备报价。你最关心的不是代码用了多少技术，而是它是否可靠。

## 具体发生了什么

演示资料写着：“PX40 使用 24V DC 电源，不能接 220V AC。”题目问：“PX40 应该用什么电源？”

助手先查知识库，再回答并附上文档来源。平台检查：

1. 答案里是否包含要求的信息。
2. 引用的是不是 PX40 电源资料，而非另一个型号。
3. 它是否真的完成查资料这一步。
4. 有没有试图越权付款或下单。
5. 这次执行有没有发生错误。

它答对这题后，还要做其他型号、采购规则和权限问题。每个版本做同样一份题集，再比较成绩。演示中的型号与政策是虚构的阅读材料，不要求你先掌握工业知识，也不能拿这些政策用于实际采购。

## 为什么不能只看总正确率

假设 100 道题里 95 道普通问题都答对了，5 道关键电源问题全错。总分 95% 看起来不错，但你不会愿意让它给客户随意推荐设备。

因此平台同时检查重点问题组。如果某一组相对旧版本退化太多，即使总分过线也拦截。另一点是，原题改写十次仍然高度相关，不能当成十种独立能力证明。这里通过 group 标注与按组重采样减少这种误判。

这些机制只能帮助检查指定题集，不能自动证明模型理解了全部业务。真实客户仍需要有代表性的题、人工验收与真实运行反馈。

## 为什么后台运行是一个技术难点

一套评测可能执行很多题。假设进程做到第五题突然退出，简单脚本可能全部重来，或者留下一堆不知道是否完整的数据。平台需要知道哪些题已经完成，以及哪个进程目前有权写结果。

这里的做法：

- **领取任务**：数据库只允许一个当前进程领取，类似取号窗口的一张有效票。
- **租约**：票有期限。持票进程消失后，别人可以接管。
- **检查点**：每做完一题，答案、执行链路和完成标记一起提交。
- **fence**：每次接管都换新编号。旧进程即使回来，也不能凭旧编号修改或发布。
- **完整发布**：所有题都完成后，才生成一份完整实验。

这些不是只写在文档里的计划。真实故障实验做到第 5 / 36 题时强制停止进程，新进程完成剩下 31 题，最终仍是 36 条 Trace、1 份实验；旧编号被拒绝。

## 术语翻译

| 代码里的名字 | 你可以怎样理解 |
|---|---|
| Dataset | 一份固定试卷：题目、标准答案、检查要求 |
| Corpus | 查阅资料：客户文档和业务规定 |
| Trace | 一道题的完整答题记录 |
| Span | 答题中的一步：查询、生成或工具调用 |
| Job | 一次后台考试任务 |
| Worker | 真正做题并保存结果的后台进程 |
| CAS | “条件没变才允许更新”，防止多人同时拿同一张票 |
| Lease | 当前执行权的有效期 |
| Fencing token | 每次接管递增的授权编号，旧编号失效 |
| Checkpoint | 一道题已完成且结果已存好的标记 |
| Experiment | 一个版本做完整套题后得到的成绩快照 |
| Gate | 发布门禁：满足所有条件才允许进入人工复核 |
| Audit | 发生了什么、为什么作出决定的记录 |

## 工业、FDE 和选题的关系

项目定位是“Agent 交付验证平台”。备件报价是展示材料，因为它自然有来源、规格和审批约束。它并不要求你把职业方向改成工业，也不说明工业项目天生更有含金量。

FDE 通常指 Forward Deployed Engineer，强调进入客户场景，连接资料、流程和软件，把东西交付落地。本项目可以展示其中一部分：把验收要求写成检查，把业务权限落实到运行时，并留下可交付证据。它同时适用于后端与 AI 平台工程方向。

目前没有真实客户访谈、采购系统集成或客户签收。简历不能写成已经完成一场真实 FDE 客户交付。

技术栈：Python、FastAPI、SQLAlchemy、SQLite WAL、HTTPX、ContextVar、原生 JavaScript、Playwright。

可按你实际理解程度改写：

- 实现每项目独立数据空间、哈希访问密钥与读写权限；验证跨项目越权查询、只读写入、密钥撤销和多进程竞争，35 项自动测试与浏览器流程检查通过。

## 面试时真正要会的内容

**为什么不能只靠线程锁？** API 和 worker 是独立进程。一个进程内的锁不会保护另一个进程，因此执行权需要放在共享持久化存储中。

**有租约为什么还需要 fence？** 旧进程可能只是暂时卡住，租约到期后别人接管，它随后又恢复。光有截止时间不足以区分谁是新负责人；递增编号让旧进程的提交失效。

**为什么 Trace 与检查点同事务？** 如果只保存答案却没记已完成，重启后会重做；如果只记完成却没保存答案，恢复时结果缺失。两者一起提交或一起回滚。

**是否实现 exactly-once？** 实现的是数据库中的幂等样本结果和有 fence 的实验发布，不是任意外部调用的恰好一次。模型计费、采购下单、付款等副作用需要另外设计幂等键、事务 outbox 与业务确认。

**为什么每项目独立数据库？** 它使项目隔离成为连接选择，而非每一条查询都依赖正确过滤 tenant_id。代价是文件、连接和跨项目运维成本，不适合直接宣称大规模 SaaS 架构。

**为什么答案正确还会失败？** 引用错误、禁止工具尝试或执行异常均会失败。验收不只检查词面答案。

**分组统计能证明安全吗？** 不能。它减轻相关问法造成的证据膨胀，但前提是 group 标注合理，问题组独立且代表实际业务。当前数据有限，报告已经提示适用范围。

**为什么没加 Kafka / Kubernetes？** 当前瓶颈与部署范围没有要求这些组件。任务状态、原子提交与失效场景优先；更大规模需要容量证据与运维需求再决定架构。

## 学习顺序

1. 先把页面三个版本跑一遍，能解释哪个被放行、哪个被拦截。
2. 沿一条 Trace 看查询、输出和失败工具，理解“证据链”。
3. 阅读 `models.py`，用上面的术语表理解每张表存什么。
4. 阅读 `jobqueue.py` 的 claim、checkpoint、publish，画出抢任务和恢复过程。
5. 运行 `fault_lab.py`，把真实结果与预期逐项对照。
6. 阅读项目隔离测试，理解为什么拿到另一个项目的 ID 也看不到数据。
7. 最后准备简历和面试叙述；能解释一处真实失败和取舍，比背技术名词更有价值。

下一阶段提升竞争力最有效的证据，是接入获准使用的真实客户资料和模型 Agent，验证更有代表性的题集、重复运行波动、人工验收与业务反馈。强项目仍然需要你掌握它；没有排名数据，无法保证“前 10%”。
